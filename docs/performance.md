# 성능·부하 기준과 권장 설정 (P31)

**이 문서의 숫자는 모두 개발 PC 한 대에서 잰 값이다**: Windows 11, PHP 8.3.35, SQLite(XAMPP 번들), Apache 2.4.58 mpm_winnt. 부하 발생기·웹 서버·워커가 같은 PC에서 돌았다. 운영 서버 사양(CPU·디스크·Linux)이 없으므로 운영 값은 **같은 도구로 운영 서버에서 다시 재야 한다**(`docs/unverified.md`).

| 20 | 36 | 0% | 0 | 95ms | 55ms | 192ms | 42ms | 27ms | 448ms |
| 50 | 84 | 0% | 0 | 318ms | 286ms | 469ms | 293ms | 120ms | 1,305ms |
| 100 | 78(포화) | 0% | 0 | 4,377ms | 1,857ms | 3,121ms | 2,227ms | 1,239ms | 2,951ms |

- **50명까지 화면 응답 p95가 0.5초 안**(명세 19.6 목표 범위). 100명에서 처리량이 늘지 않고(84 → 78) 응답이 길어졌다 — 이 PC의 CPU 포화(PHP·부하 발생기·워커가 한 PC). 오류·잠금 오류는 0이다.
- 로그인은 bcrypt(비용 11)라 동시에 몰리면 길다. 해시 강도는 낮추지 않는다.

## 3. 분석 반영 중 쓰기 대기 (B-1·B-2)

### 3.1 대량 변경 반영(B-1)

같은 명령(`seed_defects --bench --cases=A,B --ckpt=prod`, 탐침 NORMAL·NOAUTO), 2026-10-14 재측정:

| 규모·경우 | P19C 보고(이전) | P31(지금) |
| --- | --- | --- |
| 100만 A2 같은 결과 재반영 — 다른 연결 대기 최대 | 2.00초 | 1.99초 |
| 100만 B 10% 변경 — 쓰기 트랜잭션 | 8.6초 | 8.4초 |
| 100만 B — 다른 연결 대기 최대 | 8.6초 | **8.4초** |
| 50만 B 10% 변경 — 다른 연결 대기 최대 | 4.2초(1회 5.7초) | 3.9초 |

**반영 트랜잭션을 나누지 않기로 했다(검토 결과).**
- 한 Run의 반영은 "해결·재오픈·신규·존재 구간·이력·Run 요약·분석 상태 성공"을 **한 번에** 바꾼다. 묶음으로 나누면 그 사이에 다른 요청이 **반쯤 반영된 Run**을 본다. 예: 결함 목록은 일부만 해결됨, 대시보드 건수 ≠ Run 요약, 비교 패널의 신규·해결 건수가 어긋남.
- 중간에 프로세스가 죽으면 반쯤 반영된 상태를 되돌리거나 이어서 끝내는 복구 절차가 새로 필요하다. 자동 resolved·재오픈 판정은 "직전 성공 분석" 기준이라, 반쯤 반영된 Run이 기준이 되면 다음 판정이 틀어진다.
- 안전하게 나누려면 그림자 표에 쓴 뒤 한 번에 바꿔 넣거나, 버전 번호로 보이는 Run을 고정해야 한다. 둘 다 조회 쿼리 전체를 바꾸는 큰 변경이라 이번 범위(새 기능 없음)를 넘는다.

**대신 한 일(경고·안내)**:
- 쓰기 대기가 `busy_timeout`을 넘으면 지금까지는 **500 "서버 오류"**였다. 이제는 **503 `db_busy` + `Retry-After: 5`** 와 "다른 큰 작업이 끝나기를 기다리다 시간이 지났습니다. 변경은 저장되지 않았습니다. 몇 초 뒤 다시 시도하세요"를 보인다. 앱 로그에는 경고 한 줄(`DB 잠금 대기 초과`)이 남는다(`ErrorMiddleware`, 시험 `DbBusyTest`).
- 남은 위험: 결함 100만 건 규모에서 10%가 바뀌는 분석이 반영되는 약 8초 동안의 쓰기(결함 수정·로그인)는 503 안내를 받을 수 있다. 완화책은 다음과 같다.
  - 프로젝트 결함 수 경고·상한(`limits.project_defect_warn` 20만, `project_defect_max` 100만 — P19C)
  - 제외 패턴
  - 아주 큰 프로젝트가 있으면 `database.busy_timeout`을 10s로

### 3.2 웹 연결의 자동 체크포인트(B-2)

큰 반영 직후 WAL 파일이 수백 MB가 되면, 다음으로 쓰는 웹 요청 연결이 SQLite 기본 자동 체크포인트(1,000페이지)로 그 WAL을 혼자 DB로 옮긴다. 그 요청이 오래 걸린다.

| 50만 B 10% 변경 직후 다른 연결의 쓰기 대기 최대 | 값 |
| --- | --- |
| 다른 연결의 자동 체크포인트 켬(지금까지 웹 연결 기본) | **21.4초** |
| 끔(P31 웹 연결) | **3.9초** |

- **바꾼 것**: 웹 요청 연결은 `PRAGMA wal_autocheckpoint = database.web_wal_autocheckpoint`(새 설정, 기본 0 = 끔, `App::applyWebDbPragmas`). CLI 도구·워커·분석 자식은 그대로다.
- 체크포인트는 워커가 한다: 시작할 때, 분석이 끝날 때마다, 그리고 **한가할 때도 `database.idle_checkpoint_interval`(새 설정, 10분)마다** PASSIVE. TRUNCATE는 기존 규칙(`wal_truncate_threshold`)을 따른다.
- 한계: 워커가 오래 멈춰 있으면 웹 쓰기만큼 WAL이 자란다. 세션·결함 수정 정도라 하루 수 MB 수준이다. 워커 정지는 모니터링 `worker_down`(오류)으로 알린다.

바꾼 것(결과 값은 그대로 — 시험 `DefectApiTest::testSummaryCountsAgreeWithList`·`DefectListReverseTest`·`RunSourceEquivalenceTest`·`RunIntervalsTest`):

1. **요약 한 번 훑기**(`DefectQuery::summary`): 검색어·경로 포함·과거 Run이면 결함 표를 두 번(규칙 칩용·담당자 칩용) 훑지 않는다. 대신 (심각도, 상태, 규칙, 담당자)로 한 번 묶고 규칙·담당자 필터를 PHP에서 나눠 센다. 색인으로 끝나는 보통 요약은 그대로다.
2. **과거 Run 복원 원본**(`RunService::source`): 행마다 하위 쿼리 3개(심각도·상태·담당자의 "그 Run 뒤 첫 이력")를 쓰던 것을 바꿨다. 이제 그 Run 뒤 이력만 한 번 모아 결함별로 펼친 뒤 결함 표와 한 번 잇는다.
3. **뒤쪽 절반 페이지 뒤집기**(`DefectQuery::list`, `DefectFilter::orderBy(..., reverse)`): 오프셋이 전체의 절반을 넘으면 정렬 방향을 통째로 뒤집어 앞에서 고르고 결과를 다시 뒤집는다. 정렬 키가 모두 같은 방향이고 마지막이 `d.id`(유일)라 정확히 같은 페이지다. SQLite의 NULL은 가장 작은 값이라 오름차순 맨 앞이 곧 내림차순 맨 끝이다.

**새 색인·마이그레이션은 만들지 않았다(032 없음).** 느린 경우는 모두 색인을 못 쓰는 문자열 부분 일치(LIKE %…%)이거나, 과거 Run의 값 복원이었다. 색인을 더하면 분석 반영 쓰기(B-1)가 무거워진다.

**1초 목표를 넘는 것(남은 것)**:
- 검색어·경로 포함 요약 1.2초(100만 건): 메시지·경로·규칙 3열의 부분 일치를 행마다 비교한다. 목록 자체(0.24초)와 건수(0.2초)는 1초 안이다.
  - 다음 방안: FTS5 trigram 색인. 반영 때 신규·수정 행의 색인 쓰기가 늘어 B-1이 나빠지고, DB 크기가 메시지·경로 길이만큼 커진다. 반영 시간과 함께 따로 재야 한다.
  - 다른 방안: 검색 중에는 칩 건수를 늦게 채우기(화면 변경).
- 과거 Run 요약 + 상태 필터 1.6초: 과거 Run은 존재 구간 100만 행과 결함 표를 매번 이어 그 시점 값을 계산한다. 필터 없는 과거 Run 요약은 저장된 요약이라 즉시다.
  - 다음 방안: Run마다 결함 값 스냅숏 표. Run당 결함 수만큼 쓰기·용량이 는다.
- 이 규모(100만)는 프로젝트 결함 상한(`limits.project_defect_max`)이다. 경고 기준(20만)에서는 위 시간의 약 1/5이다.

## 6. 계정 CSV 일괄 처리 (B-5)

- bcrypt(비용 11) 1회 **78ms**(이 PC) → 로컬 계정 1,000행 실행 약 **78초**(P28A 79.8초와 같음). 거의 전부 비밀번호 해시이고, 쓰기 트랜잭션은 해시 뒤에 짧게 돈다.
- **바꾸지 않았다**:
  - 해시 강도는 낮추지 않는다.
  - 병렬 해시(자식 프로세스 여럿)는 웹 요청에서 PHP 실행 파일을 띄워야 하는데, Apache 모듈에서는 `PHP_BINARY`가 httpd라 믿을 수 없다.
  - 워커 작업으로 옮기면 진행 조회 API가 새로 필요해 이번 범위(새 기능 없음)를 넘는다.
- 지금 있는 완화(P28A):
  - 실행 요청만 시간 상한 600초(`AccountImportController::EXECUTE_TIME_LIMIT`)
  - 화면에 "실행하는 중… 계정이 많으면 1분 넘게 걸릴 수 있습니다"
  - 미리보기(0.01초)로 먼저 확인
- 웹 서버 쪽 시간 상한(Apache `Timeout`, 프록시 시간 상한)이 그보다 짧으면 브라우저 연결이 먼저 끊긴다. PHP는 출력하기 전까지 계속 실행되므로 계정 반영은 끝날 수 있지만, **한 번만 보이는 임시 비밀번호를 받지 못해** 사용자 관리에서 다시 발급해야 한다(미확인 — 운영 서버에서 확인할 것). 프록시를 거치면 그 시간 상한을 2분 이상으로 두거나, 1,000행보다 작게(예: 300행) 나눠 올리기를 권한다.
