# 권장 서버 사양과 디스크 용량 (P32B)

명세 19.1(권장 서버 사양)과 19.3(권장 용량 산정식)을 운영자가 바로 쓸 수 있게 정리한 문서다. 영어판: [server_sizing.en.md](server_sizing.en.md).
화면에서는 **시스템 관리 > 점검 > 용량 추정 도우미**가 아래 식으로 바로 계산한다(읽기 전용 계산, 같은 함수 `public/assets/js/lib/capacity.js`).

> 숫자의 근거를 구분해 적는다. **명세**: 요구사항 명세가 정한 값. **측정**: 개발 PC(Windows 11, PHP 8.3, SQLite)에서 잰 값(`docs/performance.md`). **추정**: 재지 않은 값 — 운영 서버에서 다시 확인해야 한다(`docs/unverified.md`).

## 1. 권장 서버 사양

| 규모(동시 사용자) | CPU | 메모리 | 디스크 | 근거 |
| --- | --- | --- | --- | --- |
| 기본(동시 분석 2개, 사용자 최대 1,000명) | **8코어 이상** | **32GB 이상** | SSD, 아래 3절 계산값 이상 | **명세** 19.1(동시 분석 2개 기준). 분석 프로세스 하나의 메모리 한도 8GB(`analysis.process_memory_limit`) × 2 + 웹·DB·OS |
| 동시 접속 50명까지 | 4코어로도 화면 p95 0.5초 안 | — | — | **측정**: 개발 PC 50명 부하 시험 p95 0.5초 안(`docs/performance.md` 2절) |
| 동시 접속 100명 | 8코어 이상 권장 | 32GB | — | **측정**: 개발 PC 100명에서 CPU 포화, 대시보드 p95 4.4초(명세 19.6 목표 3초 초과). 8코어 서버에서의 값은 **추정** — 운영 서버에서 `node tools/loadtest/run.mjs`로 확인 |

- CPU가 먼저 포화된다(측정). 메모리는 분석 프로세스 한도가 지배한다 — `analysis.process_memory_limit`을 낮추면 필요한 메모리도 줄지만, 큰 프로젝트 분석이 메모리 초과로 실패할 수 있다.
- 디스크는 SQLite·스냅샷 쓰기가 많으므로 SSD를 권장한다(추정 — HDD에서 재지 않음). 백업 폴더는 **다른 디스크**에 둔다(시스템 모니터링의 백업 카드가 같은 디스크인지 보여 준다).
- Linux에서는 ruff 메모리 제한(`prlimit`)이 적용된다. Windows는 시간·출력 한도만 적용된다(명세 19.10).

## 2. 계산식

데이터 디스크(설치 폴더의 `data/`)와 백업 디스크를 따로 계산한다.

```
분석 작업 공간 = 동시 분석 수 × (업로드 zip + 압축 해제 크기)            ← 명세 19.3
스냅샷        = 프로젝트 수 × 전체 스냅샷 보관 회수 × 업로드 zip        ← 분석 대상 파일의 zip(업로드보다 작거나 같음 — 넉넉한 쪽)
DB            = 결함 수 × 560B × 1.2 + 프로젝트 수 × Run 상세 보관 수 × 2KB + 감사 로그 보존 일수 × 하루 행 수 × 412B
로그          = 1GB(여유)
데이터 디스크 = (분석 작업 공간 + 스냅샷 + DB + 로그) ÷ 디스크 경고 비율
백업 디스크   = 보관 백업 수 × (DB + 스냅샷)                          ← 백업에 스냅샷을 넣을 때(기본)
```

| 값 | 기본 | 근거 |
| --- | --- | --- |
| 동시 분석 수 | 2(`analysis.max_concurrent`) | 명세 19.8 |
| 압축 해제 크기 | zip의 4배 | **추정**(소스 코드 zip의 흔한 압축률). 최악은 상한 `extract.max_extracted_size` 10GB |
| 전체 스냅샷 보관 | 5회(`snapshot.full_keep_count`) | 명세 7 |
| 결함 1건 | 560바이트(인덱스 포함) | **측정**(P08: 결함 10.9만 건 = 61.5MB) |
| 이력·존재 구간 여유 | ×1.2 | **추정**(결함 수정·재오픈이 많으면 더 큼) |
| Run 요약 | Run당 2KB, 프로젝트당 15개(`runs.detail_keep`) | **추정** |
| 감사 로그 1행 | 412바이트 | **측정**(P30: 100만 행 = 393MB) |
| 감사 로그 하루 행 수 | 1,000 | **추정**(관리 작업·내보내기·로그인 외 작업 수에 따라 다름 — 감사 로그 화면에서 실제 건수 확인) |
| 감사 로그 보존 | 90일(`log.audit_retention`) | 명세 19.7 |
| 디스크 경고 비율 | 80%(`disk.warn_percent`) | 명세 19.3 — 경고선 아래에서 운영하려고 나눈다 |

- **업로드 상한으로 계산한 최악의 분석 작업 공간**: 동시 2 × (2GB + 10GB) = **24GB**. `php tools/check_env.php`의 "분석 작업 최소" 값이 이것이다(업로드 시작 때도 같은 기준으로 여유를 검사한다 — 명세 19.3).

## 3. 예시(위 식, 기본 설정)

| 규모 | 입력 | 분석 작업 | 스냅샷 | DB | 데이터 디스크 | 백업 디스크 |
| --- | --- | --- | --- | --- | --- | --- |
| 소규모 | 프로젝트 10 × 결함 1만, zip 50MB, 백업 7개 | 0.5GB | 2.4GB | 0.1GB | **5.0GB** | 17.8GB |
| 중규모 | 프로젝트 50 × 결함 2만, zip 100MB, 백업 14개 | 1.0GB | 24.4GB | 0.7GB | **33.8GB** | 351GB |
| 설계 규모 | 프로젝트 200 × 결함 1만, zip 100MB, 백업 60개(매일·60일) | 1.0GB | 97.7GB | 1.3GB | **126GB** | 약 5.9TB |

- 설계 규모처럼 매일 백업을 60개 보관하면서 스냅샷까지 넣으면 백업 디스크가 매우 커진다. 스냅샷은 다시 분석하면 생기므로, 자동 백업 보관 수(`backup.retention_max_count`)를 줄이거나 오래된 묶음을 다른 저장소로 옮기는 것을 검토한다(스냅샷 제외는 명령줄 `php tools/backup.php --no-snapshots`).
- 데이터 디스크는 위 값에 업로드 상한 기준의 분석 작업 공간(24GB)을 더해 두면 큰 업로드가 와도 막히지 않는다.

## 4. 운영에서 확인

1. 설치 직후 **점검 > 용량 추정 도우미**에 예상 규모를 넣어 디스크를 정한다.
2. 몇 주 운영한 뒤 **점검 > 디스크 사용 현황**(구분별 사용량)과 감사 로그 하루 건수를 보고 추정값(압축 해제 배수·감사 로그 행 수)을 실제 값으로 바꿔 다시 계산한다.
3. 동시 사용자가 많으면 `docs/performance.md` 방법으로 운영 서버에서 부하 시험을 한 번 한다.
