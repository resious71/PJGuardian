## 무엇을 하는 기능인가

저장소를 연결한 프로젝트는 정한 간격과 시각(KST)마다 서버가 최신 소스를 가져와 자동으로 분석할 수 있습니다. 주기 분석은 [소스 저장소 연동](guide:repository)을 먼저 해야 쓸 수 있습니다.

- 별도 프로그램 없이 분석 워커가 일정을 확인해 대기열에 넣습니다. 워커가 꺼져 있으면 주기 분석도 등록되지 않습니다.
- 주기 분석은 업로드 분석과 같은 대기열에서 순서대로 실행됩니다. 동시에 실행하는 분석 수({{limit:analysis.max_concurrent}}개)도 함께 씁니다.
- 직전 성공 분석과 소스·조건이 같으면 분석을 생략하고 "성공(변경 없음)"으로 기록합니다.

## 주기 켜기

1. {{ui:icon.admin.projects}}에서 프로젝트를 열고 {{ui:projects.edit_button}}을 누릅니다.
2. {{ui:repo.title}} 아래의 {{ui:schedule.title}}에서 {{ui:schedule.field.enabled}}을 켭니다.
3. 간격을 일 단위로 입력합니다. 최소 {{limit:repository.min_interval}}, 최대 365일이며 권장은 7일입니다({{ui:schedule.week_button}} 단추).
4. 실행 시각을 KST 24시간제로 입력합니다(예: 03:00, 23:30).
5. {{ui:schedule.save}}을 누릅니다. 저장하면 다음 실행 예정 시각이 보입니다.

- 저장소 연결이 없거나, 호스트가 허용 목록에 없거나, 자격 증명을 읽을 수 없으면 입력이 꺼지고 이유가 보입니다. 먼저 연결을 고치세요.
- 마지막 연결 테스트·가져오기가 실패였거나 아직 테스트하지 않았으면 저장할 때 경고가 나옵니다. 연결 테스트로 확인하는 것을 권장합니다.
- 같은 시각에 이미 예약된 프로젝트가 있으면 그 수를 알려 줍니다. 여러 프로젝트를 같은 시각에 몰면 사용자 업로드 분석이 오래 기다립니다. 시각을 나누어 정하세요.
- 다른 관리자가 먼저 바꿨으면 저장이 거부됩니다. 화면을 새로 고친 뒤 다시 저장합니다.
- 저장소 연결을 해제하면 주기 분석은 자동으로 꺼지고 감사 로그(`schedule.auto_disable`)가 남습니다.

## 일정은 어떻게 정해지나

- 켜거나 간격·시각을 바꾸면, 바꾼 시점 이후 가장 가까운 지정 시각에 첫 실행합니다. 지난 시각을 소급해 바로 실행하지 않습니다.
- 그 뒤에는 N일마다 같은 시각에 실행합니다. KST는 서머타임이 없어 월말·연말에도 같은 시각입니다.
- 워커는 {{limit:scheduler.tick_seconds}}마다 일정을 확인하고, 한 번에 최대 {{limit:scheduler.max_per_tick}}개 프로젝트를 처리합니다(남으면 다음 확인 때).
- 워커가 꺼져 있던 동안의 밀린 일정은, 워커가 다시 켜지면 가장 최근 1회만 실행합니다. 다음 실행 시각은 현재 이후로 다시 잡힙니다.

### 건너뛰는 경우

예정 시각이 되어도 다음 경우에는 그 회차를 건너뛰고 기록만 남깁니다.

- 그 프로젝트에 이미 대기·실행 중인 분석이 있음(알림 없음)
- 디스크 사용률이 차단 기준({{limit:disk.block_percent}})을 넘었거나 여유 공간이 부족함
- 저장소 연결 없음, 허용 호스트 아님, 자격 증명을 읽을 수 없음

디스크·연결 문제로 건너뛰면 관리자에게 알림이 갑니다. 건너뜀은 실패 횟수에 들어가지 않습니다.

## 실패와 재시도

가져오기가 일시적인 이유로 실패하면 같은 분석을 다시 시도합니다.

- 다시 시도하는 실패: `repo_unreachable`, `repo_timeout`, `repo_fetch_failed`
- {{limit:repository.connect_retry_interval}} 뒤에 다시 시도하고, 모두 {{limit:repository.connect_max_attempts}}번 시도해도 실패하면 실패 1건으로 끝냅니다. 주기 설정은 그대로이고 다음 주기에 다시 수행합니다.
- 재시도를 기다리는 동안 워커는 다른 분석을 처리합니다. 그 프로젝트의 {{ui:repo.fetch_now}}은 진행 중인 분석이 있어 거부됩니다.
- 바로 실패하는 사유: `repo_auth_failed`, `repo_host_not_allowed`, `repo_tool_unavailable`, `repo_tls_untrusted`, `repo_not_found`, `repo_limit_exceeded`, `repo_empty`, `repo_unsafe_content` 등. 대상 파일이 0개여서 실패하면 기존 결함은 일괄 해결되지 않습니다.
- 재시도 횟수와 간격은 {{ui:config_settings.title}} > {{ui:config_settings.group.schedule}} 탭에서 바꿉니다.

### 알림

- 주기 분석이 실패하면 모든 활성 관리자에게 "주기 분석 실패" 알림이 갑니다. 일반 사용자에게는 만들지도 보이지도 않습니다.
- 같은 프로젝트가 연달아 실패하면 새 알림을 쌓지 않고 한 건의 횟수가 늘어납니다. 읽은 상태는 그대로이고 목록 맨 위로 올라옵니다.
- 완료 알림은 보내지 않습니다. 담당자에게 가는 새 결함·해결 요약은 업로드 분석과 같습니다.
- 관리자는 알림 설정에서 이 알림을 끌 수 있습니다.

## 성공(변경 없음)

### 생략 조건

주기 분석과 {{ui:repo.fetch_now}}은 분석 전에 원격 저장소의 최신 리비전만 확인합니다. 아래가 모두 직전 성공 분석과 같으면 가져오기·분석을 하지 않고 "성공(변경 없음)"으로 기록합니다.

- 리비전: Git은 브랜치 헤드 커밋, Perforce는 depot 경로 기준 최신 changelist
- 연결: 저장소 종류, 주소, 브랜치, 하위 경로 또는 depot 경로
- 분석 조건: 도구 버전, 서버 분석 설정과 관리자 규칙 켜기·끄기, 제외 패턴, 대상 확장자

하나라도 다르거나 알 수 없으면 분석합니다. 처음 분석하는 경우, 직전 성공 분석이 업로드였던 경우도 분석합니다. 원격 조회 자체가 실패하면 변경 없음이 아니라 평소처럼 등록되어, 가져오기 실패·재시도로 처리됩니다. 업로드 분석은 이 판단을 하지 않습니다.

Git에서 하위 경로를 정해도 변경 여부는 브랜치 헤드 커밋으로 판단합니다. 하위 경로 밖만 바뀌어도 다시 분석합니다. Perforce는 경로 기준이라 경로 밖 변경으로 다시 분석하지 않습니다.

### 강제 분석

{{ui:repo.fetch_now}}에서 변경이 없으면 화면이 "그래도 분석할까요?"를 묻습니다. {{ui:repo.force_confirm}}을 고르면 같은 리비전을 다시 가져와 분석하고 새 Run이 생깁니다. 취소하면 더 만들지 않지만 이미 생긴 "변경 없음" 기록 한 줄은 남습니다. 주기 분석에는 강제 옵션이 없습니다.

### 화면에서 보이는 모습

- 이력에 {{ui:icon.analysis_status.unchanged}} 배지와 "N회 확인 · 마지막 확인", 기준 Run 링크가 보입니다. 같은 리비전이 계속 확인되면 새 줄을 만들지 않고 한 줄의 확인 횟수만 늘립니다.
- 이력 화면의 {{ui:history.hide_unchanged}}로 변경 없음 줄을 숨길 수 있습니다.
- 프로젝트 화면의 {{ui:repo.title}} 상자에 마지막 분석한 커밋과 따로 {{ui:repo.field.last_check}}이 보입니다.
- 변경 없음은 분석이 아니므로 Run 번호, 비교 기준, 대시보드 추이, 알림에 들어가지 않습니다.
- 변경 없음은 실패 상태를 지우지 않습니다. 마지막 실제 분석이 실패였다면 변경 없음 확인이 이어져도 실패로 남고, 연속 실패 횟수도 늘거나 줄지 않습니다. 실제 분석(강제 분석 포함)이 성공해야 풀립니다.

## 주기 분석 탭

{{ui:icon.admin.tools}} > {{ui:admin_schedules.subnav}}(/admin/schedules)에서 전체 현황을 봅니다.

- {{ui:admin_schedules.scheduler_title}}: 마지막 확인 시각, 확인 간격, 도래·등록·건너뜀 건수. 오래 확인하지 않으면 지연 경고, 워커가 멈췄으면 그 안내가 나옵니다.
- {{ui:admin_schedules.list_title}}: 프로젝트마다 주기, 다음 실행, 마지막 결과(분석 링크), 연속 실패, 마지막 오류, 건너뜀 횟수
- {{ui:admin_schedules.failures_title}}: 시도 횟수와 사유, 다음 주기 재수행 예정 시각, 재시도 대기 중인 분석
- {{ui:admin_schedules.skips_title}}: 건너뛴 회차와 이유

프로젝트 목록에는 주기 분석 꼬리표와 다음 예정 시각이 붙고, 관리자에게는 연속 실패 횟수도 보입니다. 프로젝트의 분석 탭에서는 실행 주체(사용자·주기)로 걸러 볼 수 있습니다.

## 연속 실패가 이어질 때

1. {{ui:admin_schedules.subnav}} 탭에서 그 프로젝트의 마지막 오류를 봅니다.
2. 인증 실패면 연결 설정에서 토큰·비밀번호를 다시 입력합니다.
3. 접속 불가·시간 초과면 서버 상태와 네트워크(방화벽·프록시)를 확인하고, 허용 호스트 연결 테스트로 막힌 단계를 찾습니다.
4. 프로젝트 화면에서 {{ui:repo.test}}와 {{ui:repo.fetch_now}}으로 확인합니다. 실제 분석이 성공하면 연속 실패가 0으로 돌아갑니다.

연속 실패가 이어져도 주기 분석은 자동으로 꺼지지 않습니다. 당분간 멈추려면 프로젝트 편집에서 직접 끄세요.

## 주의할 점

- 워커를 오래 멈추면 그동안의 일정은 쌓이지 않고, 다시 켰을 때 1회만 실행합니다.
- 관리자가 규칙을 켜거나 끄거나 도구 버전이 바뀌면 분석 조건이 달라지므로, 다음 주기에는 같은 커밋이어도 다시 분석합니다.
- 실제 저장소와 운영 서버에서 일정대로 실행되는지는 운영 환경에서 확인할 것. {{ui:admin_schedules.subnav}} 탭의 마지막 확인 시각이 확인 간격마다 바뀌는지부터 봅니다.
